# 提醒通知与服务端 Cron 设计

## 目标

为提醒增加提前通知：普通提醒和周期提醒在发生时间前 30 分钟通知；物品保质期提醒在保质期前 2 天通知。通知由 iOS 本地通知实际展示，即使 App 未启动也可由系统触发。服务端启用 Laravel Scheduler，通过 cron 定期校正提醒数据，避免关闭、完成、删除或跨设备同步后的本地通知残留。

## 现状与范围

- 服务端已有 `reminders` CRUD、软删除、启用状态和重复规则。
- iOS 已有 `NotificationScheduler`，支持一次性、每日、每周、每月和每年规则。
- 本次不引入 APNs、设备 token 或服务端推送。
- 服务端 cron 不直接向用户发送通知，只负责维护可同步的提醒状态和运行日志。

## 方案

### iOS 本地通知

`NotificationScheduler` 根据提醒类型计算通知时间：

- `item_expiry`：`remind_at - 2 days`；
- 其他提醒：`remind_at - 30 minutes`。

一次性提醒只注册一个未来通知。周期提醒按现有规则注册未来可表达的重复通知，使用稳定的提醒 ID 标识，并在重新调度前取消该提醒的旧请求。已禁用、已完成、已删除或通知时间已过去的提醒不注册通知。

当提醒同步、创建、编辑、启停或完成时，先取消旧请求，再按最新值注册。若提前时间已经过去，则跳过该次通知，不补发历史通知。

### 服务端 Scheduler

新增 Artisan 命令（名称固定为 `reminders:reconcile-notifications`），由 `routes/console.php` 注册，并以每小时一次的频率执行。命令只处理仍有效的提醒，记录执行数量和异常日志；不修改提醒的业务时间，也不创建重复通知记录。生产环境通过系统 cron 每分钟调用 `php artisan schedule:run`，由 Laravel Scheduler 决定实际执行时机。

命令保持幂等，可重复执行。其职责是为后续同步提供稳定入口，并清理/标记不再需要客户端调度的状态；如果当前数据模型不需要额外字段，则仅执行查询校验和日志记录，避免扩展无实际消费者的通知表。

## 数据流

```text
提醒创建/同步/编辑
        -> iOS 取消 reminder-{id} 旧请求
        -> 根据 kind 与提前量计算新通知
        -> UNUserNotificationCenter 注册本地通知

cron -> Laravel Scheduler -> reminders:reconcile-notifications
     -> 查询有效提醒 -> 记录结果 -> 客户端下次同步获取最新状态
```

## 错误处理与边界

- 通知权限未授权时不阻塞提醒保存；调度失败记录本地日志并等待下一次同步重试。
- cron 单条提醒异常不应阻断其余提醒处理，命令最终以可观测日志结束。
- iOS 待处理通知数量有限，周期通知沿用系统可表达的重复触发器；后续若提醒数量超过系统限制，再增加滚动窗口策略，不在本次扩大范围。
- 时区使用设备当前 `Calendar` 计算本地通知，服务端时间继续以 UTC 序列化。

## 验证

- iOS 单元测试覆盖普通提醒提前 30 分钟、物品保质期提前 2 天、时间已过不注册、禁用/完成提醒不注册，以及周期规则的通知组件。
- 服务端测试覆盖 Artisan 命令可执行、Scheduler 已注册且重复执行不会产生业务数据副作用。
- 运行现有 iOS 与 Laravel 测试套件。
